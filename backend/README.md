# CodeVortex backend

FastAPI backend for the Customer Loyalty and Engagement Assistant. Phases 1 and 2 are implemented: contract models, configuration, authentication, CORS, consistent errors, storage interfaces and an in-memory development adapter. Customer contexts and sample drafts can be read without waiting for the full dataset or database.

The frozen integration contracts are in contracts/. Storage design is expressed through the interfaces in app/storage/interfaces.py and verified in tests/test_storage.py.

## Run locally

Use Python 3.9 or newer. The pinned dependencies were verified on Python 3.9.6.

```sh
cd backend
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements-dev.txt
.venv/bin/python scripts/create_local_env.py
.venv/bin/python -m uvicorn app.main:create_app --factory --host 127.0.0.1 --port 8000
```

If .venv and .env already exist, skip their creation. Never commit .env. The provisioning script creates random, different credentials and a reviewer token with a 24-hour expiry; it never overwrites an existing file. Its explicit allowed IDs are CUST001–CUST050, but only CUST001–CUST006 exist in the bundled temporary dataset. Permission to an ID does not imply a customer row exists. Rotate/reprovision expiring credentials locally without exposing them in logs, chat or memory.

Open http://127.0.0.1:8000/docs for API definitions and http://127.0.0.1:8000/health for liveness. Use --host 100.83.115.82 only on the backend's actual Tailscale machine. Tailnet connectivity has not been tested here. Use one worker with the temporary in-memory adapter; restart resets its writes. No AI network call, database connection or real email integration is made in these phases.

```sh
.venv/bin/python -m pytest -q
```

## Current API behavior

| Route | Behavior |
|---|---|
| GET /health | 200 liveness without auth |
| GET /api/v1/customers/{customer_id}/context | 200 permitted context; 404 absent/outside scope |
| POST /api/v1/drafts | Validate request/customer existence, then 503 pending generation |
| GET /api/v1/drafts/{draft_id} | 200 saved fixture draft, with actual customer ownership check; 404 otherwise |
| POST /api/v1/drafts/{draft_id}/review | Validate request and ownership, then 503; no approval/delivery |
| POST /internal/v1/tools/execute | Validate service/delegation scope and closed arguments, then 503 pending policy tools |

AI team owns POST /internal/v1/generate; the backend contains its exchange models, not that route. Public POST idempotency header format is enforced, and repository reservations/results exist, but HTTP reservation/replay orchestration is later work. No route claims a generation, approval or delivery succeeded before those services are implemented.

## Storage and fixture configuration

Storage is accessed through app/storage/interfaces.py and injected through create_app(settings, storage) or the get_storage dependency. The memory adapter provides context/policy reads, draft inserts and revision-checked updates, review and audit records, a unique mock outbox with contact records, and scoped 24-hour idempotency records. Transactions require an explicit commit and roll back on exceptions. Read results are deep copies. These are development capabilities, not a durable or multi-worker database.

Default fixtures: fixtures/dataset.json has six synthetic scenarios, one policy and evaluation labels; fixtures/drafts.json has DRAFT001 for CUST001. The sample draft is marked model_version=fixture_not_invoked. It is not live Gemini output, and labels are not measured model results. Runtime storage discards evaluation labels. See fixtures/README.md for scenario details.

Existing .env files need no changes for default fixtures. Optional configuration:

```dotenv
STORAGE_BACKEND=memory
DATASET_PATH=fixtures/dataset.json
DRAFT_FIXTURE_PATH=fixtures/drafts.json
```

Relative paths resolve from this backend folder, independently of the shell's current folder. A different DATASET_PATH defaults to no sample drafts; an empty DRAFT_FIXTURE_PATH explicitly disables them. The loader rejects invalid shapes, IDs/relationships, contradictory basic billing, future observed timestamps and inconsistent repeated offers before startup. Imported labels are kept out of application/AI inputs; their correctness is evaluated in Phase 3. The full requested dataset and actual database are still pending.

## Contract and security

contracts/schema.json contains 31 frozen schema definitions. app/models.py is generated by scripts/extract_contract.py from contracts/AI_SERVICE_CONTRACT.md. Both Markdown handoffs are included locally and their shared sections must stay identical. Change both handoffs before regenerating public DTOs. Storage records are separate internal models, not additional public fields.

All required fields, nullability, strict primitive types, enums, bounds and calendar formats are enforced. ReviewRequest additionally checks edit/approve/reject combinations. Full policy compliance, fresh evidence checks and canonical template validation belong to Phase 3; data validation alone does not establish eligibility or safe delivery.

Reviewers use independent expiring bearer credentials with explicit customer scopes. Backend-to-AI and AI-to-backend credentials are distinct; only the backend holds the HMAC signing secret. Scoped delegation binds customer, turn, snapshot versions, audience codevortex-ai-turn and a maximum 60-second lifetime. Later turn storage must also verify snapshot versions; until then the tool route returns 503. There is no public token issuance/login endpoint.

Every response carries X-Request-ID, X-Contract-Version and Cache-Control:no-store. Errors use the frozen Error body and do not echo raw customer inputs or credentials. JSON bodies are limited to 64 KiB public / 256 KiB internal. CORS permits only explicit frontend origins. Mock-outbox storage has no SMTP/network operation. Human approval, deterministic policy and atomic database/audit/outbox checks must exist before enabling public review actions.

Implementation references: FastAPI [validation errors](https://fastapi.tiangolo.com/tutorial/handling-errors/), [CORS](https://fastapi.tiangolo.com/tutorial/cors/), and Pydantic [strict mode](https://docs.pydantic.dev/latest/concepts/strict_mode/).

## Remaining work

Phase 3 implements deterministic classification, strategy, eligibility, consent/billing/contact checks and template rendering/validation. Later phases connect the AI service, generate drafts, choose/connect database storage, implement durable idempotency, rate limits and transactional review/audit/mock delivery, and run end-to-end evaluation. Real sending and autonomous financial actions are outside this prototype’s scope.
